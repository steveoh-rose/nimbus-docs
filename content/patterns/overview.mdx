A component tells you what a piece of the interface looks like. A pattern tells you how several pieces behave together, and what should happen when things go wrong.

<PatternIndex />

## What a pattern covers

Each pattern is written to answer the same questions, in the same order:

- **When to use it.** The situation, and where it stops applying.
- **How it behaves.** The rules, with the reasoning behind them, and Do / Don't examples where people tend to go wrong.
- **Exceptions.** Places where breaking the pattern has been discussed and is warranted.
- **A working example.** Built from the real components, with controls so you can see how the behaviour changes.

## Using patterns

Reach for a pattern before you design a flow from scratch. If a pattern almost fits, follow it and raise the gap rather than quietly diverging, so that the next person doesn't have to rediscover it.

Patterns describe behaviour, not styling. Colors, type and spacing still come from the [tokens](/docs/foundations/tokens), and the pieces themselves from the [components](/docs/components).

## Proposing a pattern

If the same decision has been made in three places, it probably belongs here. Open a discussion with the examples, then follow the [contributing guide](/docs/contributing).
